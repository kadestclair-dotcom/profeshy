## 3. What this changes downstream

- **S2 (payload reality)** now starts from hard numbers: a single house is
  a 13 MB / 131k-auction payload and commodities add 8.7 MB / 101k. No
  phone should fetch or parse this raw per user session — this is
  direct evidence for the charter §6 backend posture (server-side
  fetch, normalize, serve small) and feeds D4.
- **S3 (history):** cadence is still unknown; the recorded fingerprint
  makes the next single fetch a valid comparison point. Self-collection
  sizing can already start from T7: ~13 MB per house snapshot before
  normalization.
- **S4 (recipe/profession data)** inherits a warning, now measured: if
  53% of auctioned items have no static record via `static-forever`,
  item/recipe resolution needs its own measured source (ForeverDB is
  the named candidate) and the app must degrade gracefully — "no data"
  shown as absence (§7.5), never an invented name.
- **D4 (backend posture):** the custody pattern is proven at spike
  scale — credentials stayed on the owner's machine, nothing leaked
  into logs or artifacts (T10). One design deviation, recorded
  honestly: the design's minimal proxy stub was not built as a separate
  server; custody was instead demonstrated by the local-run channel +
  T10 search. The real backend shape remains a D4 decision at G2.
- **Kill-trigger check (§10):** not triggered. The API is live, the
  owner's token works, and the traps are quantified rather than fatal.
